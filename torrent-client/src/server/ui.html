Comment ça marche


    

  1. POST /downloads crée un job en mémoire et répond 202 avec son id tout de suite. Le travail continue en arrière-plan.
    2. 

  2. Le .torrent est téléchargé puis décodé (bencode). Le SHA-1 du dictionnaire info donne l'info-hash.
    3. 

  3. Les trackers (HTTP ou UDP) sont interrogés pour obtenir une liste de pairs.
    4. 

  4. Pairs et web-seeds (serveurs HTTP de l'url-list) sont mélangés dans une seule liste de sources. Un pool de 10 workers télécharge les pièces en parallèle, chacune vérifiée par SHA-1, et retentée sur une autre source si elle échoue.
    5. 

  5. Chaque pièce valide est écrite à son offset dans le ou les fichiers qu'elle recouvre. Cette page interroge GET /downloads/:id chaque seconde.
    6.

Cet item archive.org n'a quasiment aucun pair : le contenu vient du web-seed (HTTP Range) des serveurs d'archive.org. Il faut donc que le service ait accès à Internet, et que archive.org soit disponible.


Tous les items archive.org ne se téléchargent pas : ceux dont le _meta.xml a été régénéré après la création du torrent échouent toujours (hash de pièce différent, refus voulu), et un nœud de stockage archive.org peut être injoignable. Le message d'erreur liste alors chaque cause distincte.


Dans Docker, un outputDir sous /var/www/html/storage/app/public/movies/ atterrit dans le volume partagé avec le conteneur app. Ailleurs, les fichiers restent dans le conteneur client-torrent.
