Comment ça marche


    

  1. POST /torrents/inspect (bouton Inspecter, facultatif) lit le .torrent et liste ses fichiers, sans rien télécharger d'autre. Les index cochés partent dans fileIndexes, avec l'expectedInfoHash de l'inspection.
    2. 

  2. POST /downloads crée un job en mémoire (état checking : si outputDir contient déjà des fichiers de ce torrent, chaque pièce y est revérifiée par SHA-1 et celles qui sont bonnes ne sont pas retéléchargées ; relancer sur le même dossier reprend donc un téléchargement interrompu) et répond 202 avec son id tout de suite. Le travail continue en arrière-plan.
    3. 

  3. Le .torrent est téléchargé puis décodé (bencode). Le SHA-1 du dictionnaire info donne l'info-hash.
    4. 

  4. Les trackers (HTTP ou UDP) sont interrogés pour obtenir une liste de pairs.
    5. 

  5. Pairs et web-seeds (serveurs HTTP de l'url-list) sont mélangés dans une seule liste de sources. Un pool de 10 workers télécharge les pièces en parallèle, chacune vérifiée par SHA-1. Une pièce en échec attend un délai croissant puis repart vers la source qui l'a le moins ratée. Une source injoignable 3 fois de suite est mise de côté 30 s, une source qui envoie 2 pièces corrompues est écartée pour de bon, et les trackers sont réinterrogés quand il reste moins de 3 sources. Le téléchargement n'échoue que si aucune pièce n'aboutit pendant 2 min.
    6. 

  6. Seules les pièces qui touchent un fichier choisi sont téléchargées. Chaque pièce valide est écrite à son offset dans le ou les fichiers choisis qu'elle recouvre ; la part d'une pièce qui appartient à un fichier non choisi est jetée. Cette page interroge GET /downloads/:id chaque seconde.
    7. 



Cet item archive.org n'a quasiment aucun pair : le contenu vient du web-seed (HTTP Range) des serveurs d'archive.org. Il faut donc que le service ait accès à Internet, et que archive.org soit disponible.


Tous les items archive.org ne se téléchargent pas : ceux dont le _meta.xml a été régénéré après la création du torrent échouent toujours (hash de pièce différent, refus voulu), et un nœud de stockage archive.org peut être injoignable. Le message d'erreur liste alors chaque cause distincte.


Dans Docker, un outputDir sous /var/www/html/storage/app/public/movies/ atterrit dans le volume partagé avec le conteneur app. Ailleurs, les fichiers restent dans le conteneur client-torrent.
